### Design specificity verdict

Pass, strongly. This could not be mistaken for another product: the debugger metaphor (file-tree explorer, `README.md`, `#05 peek()`, lit line, memory strip with `[i]` slots, "returns" readout), the warm graphite palette with one ember signal, and the flat outlined isometric slabs are authored for this product and follow PRODUCT.md's stated direction. Colour is genuinely reserved for state. The risk is not genericness; it is that the debugger metaphor is applied so completely that a novice faces an IDE.

### Overall impression

The core loop is right and well made: one step, one picture, one lit line, a sentence that says why, and real code. Error copy and keyboard support are among the best I've seen in this category. The biggest opportunity is hierarchy on the trace page: everything a power user wants is visible at once, at the same 11–13px weight, so a first-time learner does not know where to look first, and on a phone the "why" text is not on screen when they press Next.

### What's working

1. **The step triad is tight.** Explanation card, lit line with per-line annotations (`line 17 top is 2, not empty`), and the diagram's state colour agree on every step checked (stack, binary search, LCS, Dijkstra). The "watch" sub-note gives the transferable idea, not just the event.
2. **Errors teach.** Live validation plus specific, example-bearing messages, `aria-invalid` and `aria-describedby` wired correctly, a polite "Copied" status, and a bad shared link degrades to the default run with an explanation.
3. **Keyboard and URL as first-class.** Arrows/Home/End/Space/R/F, focus-aware Space (does not hijack a focused button), the scrubber is a real `role="slider"` with `aria-valuetext="Step 6 of 25: Settle C at cost 1"`, a visible 2px focus ring, `touch-action: pan-y` so it scrubs on touch without trapping scroll, and every step/run is a shareable URL.

### Priority issues

**[P1] On a phone, the step explanation is below the fold while Next is pinned at the bottom.**
Location: `src/app/LessonPage.tsx` narrow branch (`[head, stage, explain, rail, …]`); `ui-shots\binary-search-4\375x812.png`, `ui-shots\stack-5\375x812.png`. Measured: `.explain p` top = 871px, viewport 812px, sticky stepbar 57px.
Why: a learner taps Next, sees blocks move, and never sees the sentence that says why. That breaks principle 1 (the step is the unit) on the platform most beginners will try first.
Fix: in the narrow flow, put the step title + one-line text directly under the stage (or inside the sticky stepbar as an expandable 2-line caption), collapse the lesson header to title + view switch (move meta and metrics below), and cap the stage height (~45vh) so stage + explanation fit in 812px. Remove the duplicate Back/Next pair inside the explain card on narrow screens (the stepbar already has them) and hide the keyboard-key legend on touch (`@media (hover: none)`).
Command: `/impeccable adapt`, then `/impeccable layout`.

**[P1] Trace page density and flat hierarchy overwhelm a first-time learner.**
Location: desktop trace (`ui-shots\stack-5\1440x900.png`, `ui-shots\dijkstra-5\1440x900.png`). Regions visible at once: header, 3–4 metrics, 3–4 stage buttons, diagram, legend, returns box, timeline, operations form (input + select + 2 buttons), memory strip with cost line, explanation + watch + nav + key legend, code with 3 tabs and annotations, checkpoints. 438 visible leaf texts at 11px and 198 at 12px on Dijkstra; explanation body is 13px, the same scale as chrome.
Why: cognitive-load checklist fails single focus, visual hierarchy, minimal choices, and progressive disclosure (4 of 8: high load). The learner's eye has to triangulate diagram (centre), text (top right) and code (bottom right) with no dominant entry point.
Fix (keep the IDE identity, change weight not content): make the explanation the loudest text on the page (15–16px, ink, title 18–20px); fold the operations form behind a "Try your own input" disclosure the first time (remember choice like the memory strip does); give the memory strip a default-folded state for first visits; demote the metrics row to one line of muted inline values; drop the per-step key legend from the card once the user has pressed an arrow key once.
Command: `/impeccable distill`, `/impeccable typeset`.

**[P1] Screen-reader users get the step's body text but not the step itself, and the diagram is a static label.**
Location: `LessonPage.tsx` line ~298 (`<p aria-live="polite">{step.text}</p>`); `src/iso/IsoScene.tsx` line 111 (`role="img" aria-label={label}` with a lesson-constant label such as "Isometric stack: blocks pile up on a base"). Document title stays "Tracepoint" on every route.
Why: on Next, NVDA/VoiceOver hear "peek() reads the top value…" but not "Step 5 of 12, Read without removing", and the diagram never describes the current state (stack contents, pointers). During Play at 2× the polite region fires every step and floods the queue. Users navigating by title/history can't tell lessons apart. WCAG 4.1.3 Status Messages (partial), 2.4.2 Page Titled.
Fix: one visually-hidden live region that announces `Step 5 of 12. Read without removing. <text>`; suppress it while playing and announce once on pause. Give the SVG a per-step `aria-label` built from the same data the memory strip uses (e.g. "Stack, bottom to top: 4, 9, 2. top = 2"), or `aria-describedby` the memory strip. Set `document.title` to `Stack · step 5 · Tracepoint`. Give the memory strip real list/table semantics in the cell layout (only the table layout has roles today).
Command: `/impeccable harden`.

**[P2] Feature discoverability: speed, Show all, colour key, kind chips.**
Location: stage toolbar (`1×` button), conditional "Show all", "?" popover, chips like PEEK/CHECK/ADD.
Why: `1×` reads as a label, not a control; "Show all" appears and disappears per lesson/step and shifts Reset/Play; the colour meaning lives behind an icon. Recognition over recall fails.
Fix: label the speed control "Speed 1×" (or a 3-way segmented 0.5/1/2); keep "Show all" always rendered and disabled when nothing is cropped so the toolbar never reflows; add a title/tooltip to each kind chip and link the legend to the "?" colour key; on first trace visit show a one-line dismissible tip under the timeline: "← → to step · drag the timeline · type your own operations below".
Command: `/impeccable clarify`, `/impeccable onboard`.

**[P2] No first-run orientation; home is the Foundations README.**
Location: `/` → `GuidePage` for foundations (`ui-shots\home\1440x900.png`).
Why: a first-time visitor lands mid-curriculum with no statement of what a "trace" is or that they can type their own input (the product's positioning). The CTA "Start with Big-O by counting" is good but the core interaction is never previewed.
Fix: a single compact intro block on `/` above the README (one sentence of what Tracepoint does + a 3-step inline mini-trace or a looped still from the stack lesson + "Start the course"), shown until the first lesson is opened. No modal tour.
Command: `/impeccable onboard`.

### Persona red flags

**Jordan (first-timer, CS student meeting stacks):** lands on a README in a file tree; on the trace page sees 4 metric labels in caps (`NEXT WRITE`, `FREE`), a chip `PEEK`, `IN MEMORY: INT[] DATA`, `O(1) push` before reading a single sentence. "Next: dijkstra(A)" on Dijkstra gives no hint what the next step does. Practice/Quiz at ≤1120px drop the "soon" tag and look like live tabs that do nothing.

**Sam (screen reader / keyboard):** 16 tab stops before reaching Back/Next on desktop (toolbar, scrubber, form, memory summary come first); no skip link to the step controls. Hears step text without step number or title; diagram is a constant label. Focus ring itself is clear (2px ink, offset) and the scrubber slider is well labelled.

**Casey (phone):** taps Next in the thumb bar, explanation stays off-screen; stepbar label truncates ("mid =…"); code language tabs are 25px tall; the keyboard legend takes two lines of space on a device with no keyboard; two Next buttons on screen when scrolled to the explanation.

**Interview reviser (project persona, revising Dijkstra):** well served: keyboard, speed, custom graphs, Python/C++ tabs, URL per step. Friction: Dijkstra edge weights and `d=∞` tags render tiny at the default camera (`ui-shots\dijkstra-5\1440x900.png`), and the code card header crams `pq = [C:1, B:4] dist = A:0 B:4 C:1 D:∞ E:∞` into three wrapped lines (also LCS: `i = 3 j = 2 common = ""`).

### Minor observations

- Theory/trace view switch moves (top-right on trace, under subtitle on theory) and the selected state is inverted ink in one and light chip in the other depending on theme; keep it in one spot.
- Key legend in the explanation card wraps mid-pair at 1440 ("· R" end of line, "reset" next line).
- The `.btn.cue` Next button pulses forever (`animation: cue 2s infinite`). It is calm in amplitude, but an endless pulse on the primary control contradicts principle 2 for long sessions; stop it after the first interaction or after 3 cycles. Reduced-motion users get a static ring, which is correct.
- Guide prose: JetBrains Mono at 15–17px with ~1.6 line height and ~70ch measure reads acceptably for the Core idea block; the long `dl.terms dd` definitions and case-study `dd` are in `--muted` at 15px on a 2-column grid, which in a monospace face makes long runs tiring. Keep the font; set body definitions to `--ink`, cap measure at ~62ch for mono, use `text-wrap: pretty`, and add a touch more paragraph spacing. The explanation card's 13px mono at 44ch is the one place prose is too small.
- "On this page" in the guide has no visible current-section state while scrolling.
- `.btn.primary` dark/light inversion reads well in both themes; dark theme looks deliberately tuned (warm, not pure black).

### Checks that passed (verified)

- Contrast, light theme (computed): muted text 6.35:1 on surface, `--muted-2` 5.71:1, ink 15.7:1. Dark theme: muted 7.28:1, body 14.5:1. Token comment claims 4.5:1 everywhere; spot checks agree. Colour is never the only carrier in diagrams: pointer tags (`top`, `lo`, `mid`, `hi`, `s`, `u`, `min`) and the explanation text carry state too, though Dijkstra's "being settled" amber vs "settled" sand vs "out-of-date" are close for deuteranopes; the tag labels save it.
- Focus: `:focus-visible` 2px ink outline with offset globally; scrubber has its own 4px-offset ring (`browser\dijkstra-6-light-scrubber-focus.jpg`).
- Reduced motion: intentional, not a global kill — camera glide jumps (`IsoScene.tsx` `reduced()`), enter/leave animations and the playhead tick are removed, the pulsing Next becomes a static ring, smooth scroll becomes instant, guide ink animation skipped. Autoplay remains user-initiated only.
- Forced colours: explicit `@media (forced-colors: active)` rules for scrubber, lit line, selected tabs.
- Form: labelled input, `aria-invalid`, `aria-describedby` switching between hint/check/error, `role="alert"` on Run failure, `role="status"` on copy.
- Bad input probes (stack): `pusj 9` → `Unknown operation "pusj". Use push, pop, peek.`; empty → `Type at least one operation.`; 21 ops → `Keep it to 16 operations or fewer so the steps stay readable.`; `push abc` → `push needs a whole number from 0 to 99, like "push 7".`; `pop` on empty and `PUSH 4` run (case-insensitive, empty-pop traced as a throw). Failed runs keep the previous run on stage and the draft in the box.
- Responsive: no horizontal scroll at 375; stepbar respects `env(safe-area-inset-bottom)`; scrubber `touch-action: pan-y` with pointer capture and cancel handling (layout verified in emulated 375x812 Chromium; real touch drag not exercised).
- Persistence: theme, language, memory-strip fold, Show-all choice, explorer state and progress stored with try/catch fallbacks.

### Patterns and systemic issues

- The type scale bottoms out at 11px and that bottom is the majority: chrome, labels, hints, legends, key caps, metrics, memory indices all share it, so the explanation (13px) barely separates from chrome. A three-tier scale for the trace page (content 15–16 / chrome 12 / micro 11) would fix most of the hierarchy complaint without removing anything.
- Every power feature is always visible; there is no first-visit vs returning-visit distinction anywhere on the trace page, although the app already remembers per-viewer choices (memory fold, Show all), so the mechanism exists.
